# LLM Wiki 四阶段维护工作流

> 基于 Karpathy LLM wiki 范式 + DAIR.AI 对该范式的四阶段拆解（ingest / extract / organize / maintain）。

## 角色定位

你是知识库的"编译器 + 维护者"。原始资料是源代码，wiki 是编译产物。你的职责是把零散资料编译成结构化、可检索、可持续维护的 Markdown 知识库，并保持它的内部一致性。

## 推荐目录结构

一个完整的个人 LLM wiki 建议这样组织（以内容创作为例）：

```
my-wiki/
├── README.md              # 首页索引：列出所有页面 + 分类摘要
├── SCHEMA.md              # 本 wiki 的 Schema 定义（每类页面的字段规范）
├── inbox/                 # 摄入区：原始资料暂存（未处理）
│   ├── web-clips/         # 网页剪藏
│   ├── notes/             # 手动笔记
│   └── imports/           # 文档导入
├── brand-wiki/            # 品牌资料库（见 wiki-schema-templates.md）
├── industry-wiki/         # 行业语料库
├── hits-wiki/             # 历史爆款库
└── benchmarks-wiki/       # 对标账号档
```

`inbox/` 是唯一允许"原始、无结构"的地方；其余目录的每个文件都必须符合对应 Schema。

## 四阶段工作流（严格顺序）

### 阶段 1：Ingest（摄入）

**目的**：把外部资料收进 `inbox/`，不做任何加工。

**资料来源**：
- **网页剪藏**：Obsidian Web Clipper / 浏览器扩展抓取的文章 → 存入 `inbox/web-clips/`，文件名用 `YYYYMMDD-简短标题.md`
- **手动笔记**：用户口述或粘贴的零散信息 → `inbox/notes/`
- **文档导入**：PDF / Word / 飞书文档导出的 Markdown → `inbox/imports/`

**摄入时的最小动作**：
- 文件顶部加 frontmatter：`source:`（URL 或"对话"或"手动"）、`captured:`（日期）、`status: inbox`
- 不做内容改写、不做结构化——原样保留

**完成标志**：`inbox/` 里有了原始文件，但还没动 wiki 主体。

### 阶段 2：Extract（抽取）

**目的**：读 `inbox/` 的原始文件，按 Schema 抽取结构化条目，写入对应 wiki 页面。

**关键：先有 Schema 再抽取**。
- 如果目标 wiki 已有 Schema（见 `wiki-schema-templates.md` 或用户的 `SCHEMA.md`），直接套用。
- 如果没有 Schema，**先和用户一起定义 Schema**，再抽取。

**抽取工作流**：
1. 读一个 `inbox/` 文件
2. 判断它属于哪个 wiki（brand / industry / hits / benchmarks / 其他）
3. 按 Schema 抽取字段——一条原始资料可能抽出多个条目（例如一篇行业报告可能抽出"行业术语"3 条 + "痛点"2 条 + "数据源"1 条）
4. 写入目标 wiki 页面：
   - **新条目**：新建页面，加 frontmatter，加双向链接 `[[相关页面]]`
   - **已有条目**：更新现有页面，合并信息（不是覆盖，是补充）
5. 处理完的 inbox 文件：把 frontmatter 的 `status` 改为 `extracted`（不删除，留作追溯）

**抽取硬约束**：
- **忠于原文**：抽取是结构化，不是改写。原文没说的不要杜撰。
- **标注来源**：每个条目的 `source` 字段指向原始资料。
- **一次一库**：不要跨库混抽，避免字段错配。

### 阶段 3：Organize（组织）

**目的**：让 wiki 内部"织成网"，而不是一堆孤立的页面。

**组织动作**（每次抽取后增量做）：
1. **更新双向链接**：新页面 A 引用了已有页面 B，那 B 也要加 `[[A]]` 的反向链接（Obsidian 等工具会自动生成反向链接，但显式写出更稳）
2. **更新首页索引** `README.md`：新页面要加到对应分类的列表里，附一句话摘要
3. **刷新分类摘要**：如果一个分类下的页面数变了，刷新该分类在首页的概述
4. **处理交叉引用**：新条目可能和多个现有条目相关，把这些关系都建链

**组织的判断标准**：随便点开一个页面，能不能顺着链接走到相关页面？如果能，组织合格；如果它是"孤儿"（没人链它、它也没链别人），需要补链接或归并。

### 阶段 4：Maintain（维护）

**目的**：随时间推移，保持 wiki 不腐坏。

**维护场景**：
- **冲突检测**：新资料和已有页面矛盾时，不要静默覆盖。在页面顶部加 `> ⚠️ 冲突：...` 标注，等用户裁决。
- **合并重复**：发现两个页面讲的是同一件事，合并成一个，把另一个改成重定向（`# 已合并至 [[目标页面]]`）。
- **刷新摘要**：页面正文更新后，首页索引和分类摘要里的一句话描述也要同步。
- **过期标注**：明显过时的数据/观点，加 `> 📅 最后核实：YYYY-MM-DD`，提醒后续核对。

**定期 lint**（用户主动要求时全量跑一次，见下方清单）。

## wiki-lint 自检清单

当用户要求"检查 wiki"或每次大规模更新后，按此清单逐项过：

| # | 检查项 | 不通过怎么办 |
|---|---|---|
| 1 | 每个页面都有符合 Schema 的 frontmatter | 补齐缺失字段，或与用户确认是否该删 |
| 2 | 每个页面至少有 1 个双向链接（首页 README 除外） | 补链，或判断是否该归并到其他页 |
| 3 | 每个双向链接 `[[X]]` 指向的页面 X 确实存在 | 修正链接，或创建占位页面 |
| 4 | 没有孤儿页面（没人链它、它也没链别人） | 补链到相关页面，或从首页索引加一个入口 |
| 5 | 首页 README 的页面列表与实际文件一致 | 同步增删 |
| 6 | 每个条目有 `source` 字段 | 能补则补，不能补标注 `source: 未知` |
| 7 | 无未解决的冲突标注（`⚠️`） | 逐个与用户确认后处理 |
| 8 | 分类摘要与该分类下页面内容匹配 | 刷新摘要 |

## 与创作技能联动（关键章节）

wiki 的价值在于被创作技能引用。以下是标准联动协议：

### 创作时"挂载" wiki 的约定

当用户通过 `growth-content-*` 或 `content-toolkit` 做创作，且需要引用私有资料时：

1. **声明挂载**：创作开始前说明"本次挂载 X-wiki，读取了以下页面：..."
2. **标注引用**：产出中引用 wiki 内容时，用 `[[页面名]]` 标注来源（类比学术引用）
3. **不杜撰**：wiki 里没有的信息，不要假装有；要么说"wiki 未收录，建议补充"，要么明确标注是外部推测

### 创作产出的回流

创作/分析过程中产生的新知识，应该回流到 wiki：

| 产出场景 | 回流到哪 | 怎么回流 |
|---|---|---|
| 用 `content-toolkit/competitor-pattern-mining` 拆了一条竞品爆款 | `hits-wiki/` 或 `benchmarks-wiki/` | 按 Schema 新建一条爆款拆解条目 |
| 用 `growth-content-strategy/benchmark-analysis` 拆了对标账号 | `benchmarks-wiki/` | 新建/更新对标账号页面 |
| 创作中发现新的品牌话术/产品卖点 | `brand-wiki/` | 经用户确认后补充 |
| 分析出新的行业规律 | `industry-wiki/` | 经用户确认后补充 |

**回流硬约束**：未经用户确认的推测性结论，不要直接写进 wiki——wiki 是事实库，不是草稿本。

## 硬约束（本工作流通用）

- **先 Schema 后内容**：没有 Schema 不抽取。
- **inbox 与 wiki 分离**：原始资料永远在 inbox，结构化条目才进 wiki。
- **忠于原文**：抽取是结构化，不是改写或扩写。
- **来源可追溯**：每个条目必须能追溯到原始资料。
- **冲突不静默**：遇到矛盾标注出来，不擅自覆盖。
- **增量维护**：每次抽取顺手做组织（阶段 3），不要攒一大堆再整理。
